THE IDEA
Phasmid は Janus＝二つの面。見せる面（capture-visible／圧力下で開示する、ありふれた面）と 守る面（protected local state／可視経路の外）を一つの vessel に持つ。全編この対比を貫く — “見せたものが全てではない。” 信頼の核は2点：cue ≠ key と 倫理（Allowed / Disallowed）。必ず明瞭に言い切る。
新構成の落とし穴 · 2件
①Step 3 が Step 4 を破壊しうる。 PHASMID_DURESS_MODE=1 だと第1モード（＝囮の面）へのアクセスが自動 purge を発火し、Step 4 で開くはずの面が Step 3 の時点で消える。PHASMID_PURGE_CONFIRMATION=0 だと成功した復元すべてが他方を purge する。どちらも既定安全（false / true）で起動スクリプトも設定しないが、両面を連続で開くのは本構成が初めてなので、この落とし穴も本構成で初めて意味を持つ。登壇前に env | grep PHASMID で両方が残っていないことを確認する。
②2つのダウンロードは同名になる。 create_file_response は元のファイル名を意図的に使わず、常に retrieved_payload.bin を返す（ファイル名がどの面が開いたかを漏らすため）。よって Step 4 の「別のファイル」はファイル名では示せず、中身を開いて見せるしかない。さらに2つ目が retrieved_payload(1).bin になってダウンロード欄で衝突するので、事前にダウンロードフォルダを空にしておく。聞かれたら capture-visible discipline の実例として説明できる。
前版から変わった判断 · 2件
①「1容器・2パスワード・2ファイル」の対比は、現行の手順表から落ちている。 Step 2 で2つの Face を登録するところまでは同じだが、Step 3 で開くのは片方だけで、2つ目のパスワードで別のファイルを出す beat が無い。枠（~7:30）と、Step 4b をどう置くかの判断による。 戻したいなら Step 3 の直後に +0:30 で挿入できる（物体Bに持ち替え → 2つ目のパスワード → 別の中身を開いて見せる）。両方の Face は Step 2 で既に登録済みなので追加の準備は要らない。 入れる場合も Step 4 の「物体だけ外す」対比は必ず残すこと — 片方だけでは、前者は二重底のパスワード管理に、後者は物体認証つき暗号化に見える。
②破壊を壇上で実演する道が開いた。 前版は「破壊は実演しない」と決めていた（理由は Part 8 のボックスに残してある。法的整合の論点は今も生きている）。#191 で画面も操作手順も一切増えない形になったため、Step 4b として任意ステップに格上げした。ただし不可逆で、実施すると次の Audit の数字が「消したあとの状態」を映す。当日判断でよい。

v4 · 何が変わったか
①製品モデルが確定した。 囮ファイルはツールが作らない — 利用者が用意する。 生成機能は「空き領域の填充」へ降格し、画面上も Free Space Filler / Fill Free Space に改称済み。可信性スコアの表示は撤去した（分量しか測れないものを判定に見せていたため）。②パスフレーズは3つ（真の復号／真の破壊／偽の復号）。③強要下では開示しない — 制限パスフレーズは破壊資格であり取出資格ではない。④証明は「成功」ではなく「対比」で作るという方針を確立した。 物体を外して失敗させる否定形の対比が cue≠key の唯一の実証であり、以降の版はこの原則を保ったまま構成だけを更新している（現行は Step 4）。
v0.4.0 · 何が変わったか
①Vessel の管理は TUI、日常の運用は WebUI という役割分担が確定した。TUI が Vessel の 作成・削除を担う（del で Delete Vessel — 使い終わった Vessel を完全に消去し、容量も解放する。強要下の destroy-vessel とは別物で、こちらは平時の後片付け）。WebUI は既存 Vessel への Store/Retrieve だけを担う。②WebUI にロール別アクセストークンを追加。 store トークン（Face 登録・保存に到達）と recover トークン（復号・破壊のみ、Face 選択も制限パスフレーズ欄も一切出ない）を分離。固定値は PHASMID_STORE_TOKEN / PHASMID_RECOVER_TOKEN（役割トークンが1つでも発行されると PHASMID_WEB_TOKEN は /unlock に受理されなくなる）。③WebUI 経由の Store/Retrieve 統合経路を実機で検証済み。 Face 1・Face 2 の登録から復元まで WebUI だけで完結する流れを確認した。デモ本編もこれに合わせて改訂した — Step 2「Bind」と Step 3「Operate（正しい物体での復元）」を TUI の Add File から WebUI の Store/Retrieve 画面へ移した。カメラのライブ映像と一致バッジが見える分、旧来の TUI 版より説得力が上がる。Step 4「物体を完全に外して失敗させる」だけは TUI に残した（この特定の否定証明は今回の実機確認では WebUI 側で再検証していないため）。④その過程で見つけた3件の不具合を修正済み： Retrieve 成功後にカメラが停止する問題／Vessel 新規作成時に前の Vessel の物体キューが残留し新規登録をブロックする問題／Store 画面で Entry（Face）を明示的に選べなかった問題。⑤Expert フッタの安全端末幅が 123→145 桁に変更（Access Tokens・Delete Vessel のキー追加のため）。
最新 · 何が変わったか
①デモの主張を1段階正確にした。 旧構成は「正しい物体で開く」までしか見せておらず、観客にはただのパスワード復号に見えていた。この版で 同じ vessel を2つのパスワードで開き、別々のファイルが出てくる対比を導入した（/retrieve は入力パスワードと撮影した cue で全 Face を順に試すので追加実装は不要）。0.6.0 の手順表からはこの beat は外れている — 枠と Step 4b の兼ね合いによる。戻し方は上のボックス参照。
②「強要されてもデータを守る」とは言わない。 守るのは開示範囲であってデータではない。「強要されたパスワードでデータは守れない。守れるのはすべてが出ないこと」— これが Slide 22 の Data-existence deniability: partial と整合する唯一の言い方。
③破壊は壇上で実演しない（0.6.0 で判断が変わった → 上のボックス・Step 4b）。④TUI の Add File・Doctor・Inspect を非活性化（#169・WebUI と重複）。Recover File と Audit は意図的に残した（Audit は Step 5、Recover File は WebUI が落ちたときの否定証明用）。⑤Expert フッタの安全端末幅が 145→124 桁に下がった（フッタの項目が2つ減ったため）。⑥Vessel レジストリの Face 詳細を暗号化（#178/#180）— 以前は物体の知覚ハッシュと破壊用パスフレーズの検証子が平文だった。⑦TUI は「構造が見える研究・検査面」と明文化し、実地では PHASMID_FIELD_MODE=1 で絞る（→ 後述）。
0.6.0 · 実機で何が変わったか
ここから下は Pi Zero 2 W の実機で全手順を通した結果に基づく。設計からの推測ではない。
①物体の登録が2段階撮影になった（#184/#187）。 1 · Capture empty scene（物体をフレーム外にして空の視野を撮る）→ 2 · Capture access object（物体をかざして撮る）。この2枚の差分だけが特徴として登録される。従来は視野全体を鍵にしていたため、三脚で固定した背景そのものが鍵になり、物体を隠しても開いてしまっていた — 旧版の否定証明は証明になっていなかった。加えて保存の瞬間にも一致を再確認するので、撮ってから物体を下ろして Protect file を押すと拒否される。
②否定証明（物体なし→拒否）を WebUI に移した。 実機で WebUI 経路の拒否を確認済み。Step 3（成功）と Step 4（失敗）が同じタブで連続する — 画面を切り替えないこと自体が「他は何も変えていない」ことの担保になるので、TUI に置いていた旧構成より論証が強い。プロジェクタ切替は1往復のまま（折り返しが Step 4→5 に移った）。
③破壊がパスワードで制御できるようになった（#191）。 Step 3・4 と同じ入力欄にアクセスパスワードではなく破壊パスワードを入れると、かざしている Face が消える。画面は何も変わらず、応答は打ち間違えと完全に同じ No valid entry found.。もう一方の Face は無傷。これで「破壊は壇上で実演しない」という前版の判断が変わった（→ Step 4b）。
④復元時の照合が厳しすぎた件を調整（#188）。 絶対値の閾値（50/30）は視野全体を登録していた頃の校正で、物体だけを切り出すとキーポイントが72程度まで減り、同じ数を要求すると6回中1回しか一致しなかった。テンプレート自身のキーポイント数に対する割合（25% / 15%）に変え、絶対値で頭打ちにしてある（従来より厳しくなることはない）。判別力は落ちない — 空シーンも別の物体も good match が0なので、境界は 42 対 0 であって 42 対 49 ではない。
⑤破壊経路の実機検証で3件の不具合が出て修正済み（#190/#192）。 60秒ロックが解けたあとも1回間違えるだけで再ロックする／CLI 側の失敗カウンタが2回目以降を記録できていない／WebUI で登録した Face は CLI 由来の指紋を持たないため破壊が常に失敗する。いずれもリハーサルで踏む類のもので、踏んだ。

TUI は「見える面」· 意図
TUI は二面構造が意図的に見える研究・検査面だと明文化した（docs/TUI_OPERATOR_CONSOLE.md）。Simple 画面の Files 列は全 Face の合計を出し、Audit は Tracked Faces を報告する。モデルが動いていることを検証・実演するには構造が読めた方がよいからで、隠しているのではなく選んでいる。
だから壇上に出すのは TUI ではなく役割別 WebUI（recover トークンは Face セレクタも Face 数も Store/Maintenance 導線も出さない）。実地では PHASMID_FIELD_MODE=1 にすると全 Face 合計が - に縮退する。強要下で TUI を開いてはいけない — 隠している側の存在と分量を自分から渡すことになる。

実機で実際に踏んだものだけを挙げる。
①マウスでボタンを押す — SSH 越しのターミナルではクリックが Textual に届かない。ボタンはフォーカスされるだけで発火しない。全操作を Tab / Shift+Tab と Enter で行う。
②壇上で Fill Free Space を実行 — 64 MiB / 15% で実測約4分。枠は1:20。事前に埋めておき、壇上では Inspect Free Space のみ。
③囮をツールに作らせる — 生成される填充物は汎用ファイルであり、開示材料としての真実味がない。囮は運用者が用意する。
④素の phasmid で起動 — libcamera のログが TUI を破壊する／WebUI がラップトップから見えない／Ctrl+S が XOFF に食われる。scripts/pi_zero2w/run_demo_console.sh を使う。
⑤成功例だけを見せる — 物体キューが効いている証明にならない。観客にはただのパスワード復号に見える。Step 4（物体なし→拒否）を、Step 3 と同じタブのまま必ず見せる。
⑥端末幅を124桁未満にする — Expert フッタから w WebUI が無言で消える。省略記号も出ない。露出した WebUI を引っ込めるキーが画面から失われる（#169 でフッタが2項目減り、145→124 桁に下がった）。
⑦TUI で Add File を探す — #169 で非活性化済み。Operation セレクタには Recover File / List Files / Remove File しか出ない。保存はすべて WebUI の Store 画面で行う。
⑧物体をかざしたまま 1 · Capture empty scene を押す — 空の視野に物体が写り込むと差分が物体を切り出せない。1枚目は必ず物体をフレーム外に。 逆に2枚目を撮ってから物体を下ろして Protect file を押すのも拒否される（0.6.0 は保存時にも一致を再確認する）。撮影から保存まで、かざし続ける。
⑨TUI で役割トークンを発行しようとする — 起動スクリプトが PHASMID_STORE_TOKEN / PHASMID_RECOVER_TOKEN を固定するため、その間 t 画面からの発行・失効は AccessTokenEnvPinned で拒否される。t 画面は「ここで発行・失効できる」と見せるだけにし、ログインは固定値で行う。

Pre-flight — 事前準備 OFF STAGE
